## 二、产品负责人 (Product Owner)

### 2.1 岗位定位
产品价值的唯一负责人，连接业务方与开发团队，确保团队始终在做"正确的事"。

### 2.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **需求管理** | 收集、分析、优先级排序业务需求，维护产品待办列表（Product Backlog） |
| **价值定义** | 为每个用户故事定义业务价值、验收标准（Acceptance Criteria） |
| **决策权威** | 对Backlog内容、优先级、发布范围拥有最终决定权 |
| **干系人沟通** | 代表业务方参与迭代评审，收集反馈并转化为新需求 |
| **发布规划** | 制定版本路线图（Roadmap），预测交付节奏 |

### 2.3 日常工作清单

- [ ] **每日**：查看团队进度，回答需求澄清问题，处理突发业务变更
- [ ] **每周**：主持Backlog梳理会（Refinement），确保下个Sprint需求就绪
- [ ] **每Sprint**：
  - Sprint计划会：明确Sprint目标，确认故事范围
  - 迭代评审会：验收已完成功能，决定是否发布
  - 迭代回顾会：参与流程改进讨论
- [ ] **每季度**：更新产品路线图，评估市场反馈与业务战略对齐度

### 2.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 产品愿景与战略文档 | Markdown | 每季度 | `/docs/product/vision.md` |
| Product Backlog | 项目管理工具（Jira/禅道） | 实时 | 工具平台 |
| 用户故事卡片 | 统一模板 | 每周 | 工具平台 |
| 发布说明 (Release Notes) | Markdown | 每版本 | `/docs/release/` |
| 业务验收报告 | Excel/PDF | 每版本 | `/docs/acceptance/` |

**用户故事标准模板**：
```markdown
## 故事编号：US-XXX
**作为** [角色]  
**我希望** [功能/能力]  
**以便** [业务价值/目的]

### 验收标准 (AC)
- [ ] AC1：给定[上下文]，当[操作]，则[预期结果]
- [ ] AC2：...

### 优先级：P0/P1/P2/P3
### 故事点：?
### 关联需求：RQ-XXX
### 备注：UI稿链接、数据埋点需求等
```

### 2.5 工作要求

- **可用性**：工作日至少 70% 时间可被团队随时联系（需求澄清）
- **决策时效**：团队提出的需求澄清问题，24小时内必须响应
- **Backlog健康度**：每个Sprint开始前，Top 20% 故事必须达到"就绪"（Ready）标准
- **拒绝镀金**：不得在当前Sprint中途插入新需求；紧急变更需走变更流程，置换等价故事点

### 2.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 需求交付准时率 | ≥ 90% | 每Sprint |
| 需求返工率（因需求不清导致） | ≤ 10% | 每季度 |
| 业务方满意度 | ≥ 4.2/5 | 每季度 |
| Backlog梳理完成率 | 100%（Top 20%就绪） | 每Sprint |

## 三、Scrum Master / 敏捷教练

### 3.1 岗位定位
团队流程的守护者、障碍的清除者、敏捷实践的教练。不管理团队，而是服务团队。

### 3.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **流程护航** | 确保Scrum/敏捷仪式（站会、计划会、评审会、回顾会）高效进行 |
| **障碍移除** | 识别并解决团队内外的阻塞因素（Blocked Items） |
| **教练辅导** | 引导团队自组织，提升敏捷成熟度 |
| **数据透明** | 维护团队看板、燃尽图/燃起图，确保进度可视化 |
| **冲突调解** | 促进团队健康协作，处理人际冲突与决策僵局 |
| **持续改进** | 推动回顾会改进项落地，追踪流程优化效果 |

### 3.3 日常工作清单

- [ ] **每日**：主持15分钟站会（Daily Standup），更新障碍看板，跟进昨日阻塞项
- [ ] **每周**：与PO进行1对1，同步Backlog健康度；与TL进行技术债务评估
- [ ] **每Sprint**：
  - 计划会：引导估算与承诺，防止过度承诺
  - 评审会：确保演示聚焦价值，收集可执行反馈
  - 回顾会：采用不同 facilitation 技巧，产出 ≤ 3 个改进项
- [ ] **持续**：维护团队速度（Velocity）数据，预测交付能力；组织敏捷培训

### 3.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 团队工作协议 (Working Agreement) | Markdown | 每季度 | `/docs/team/working-agreement.md` |
| Sprint迭代数据报告 | Excel/图表 | 每Sprint | `/docs/sprint/metrics/` |
| 障碍追踪日志 | 表格/工具 | 实时 | 工具平台 |
| 回顾会纪要及改进项追踪 | Markdown | 每Sprint | `/docs/retrospective/` |
| 团队敏捷成熟度评估 | 雷达图+报告 | 每季度 | `/docs/team/maturity/` |

**Sprint数据报告模板**：
```markdown
## Sprint XX 数据报告
- **计划故事点**：XX
- **完成故事点**：XX
- **完成率**：XX%
- **新增/变更故事点**：XX（变更率）
- **平均周期时间**：X天
- **阻塞项数量**：X（平均解决时长：X小时）
- **缺陷逃逸率**：X%
- **团队速度趋势**：↑/↓/→
- **改进项完成**：X/3
```

### 3.5 工作要求

- **中立性**：不兼任技术决策或需求决策，保持流程中立
- **响应时效**：团队上报的阻塞项，4小时内必须响应，24小时内必须推动解决或升级
- **会议纪律**：站会严格控制在15分钟；计划会不超过4小时（2周Sprint）
- **保密原则**：回顾会内容遵循"Vegas规则"（会上说的，留在会上）

### 3.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 阻塞项平均解决时长 | ≤ 8小时 | 每Sprint |
| Sprint目标达成率 | ≥ 85% | 每季度 |
| 回顾会改进项完成率 | ≥ 80% | 每季度 |
| 团队满意度（对SM服务） | ≥ 4.5/5 | 每季度 |
| 敏捷仪式出席率 | 100% | 持续 |

## 四、前端开发工程师

### 4.1 岗位定位
用户界面的实现者，负责Web/App端的交互体验、视觉还原与性能优化。

### 4.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **界面开发** | 按UI稿实现页面，确保像素级还原与跨端兼容 |
| **交互实现** | 实现动画、表单校验、路由跳转、状态管理 |
| **接口联调** | 与后端对接REST/GraphQL接口，定义前后端契约 |
| **性能优化** | 首屏加载优化、代码分割、懒加载、缓存策略 |
| **组件沉淀** | 维护团队UI组件库，提升复用率 |
| **单元测试** | 编写组件级单元测试（Jest/Vitest + React Testing Library） |

### 4.3 日常工作清单

- [ ] **每日**：参加站会汇报进度；提交代码前自测并通过CI门禁
- [ ] **开发中**：
  - 领取用户故事 → 技术方案设计（复杂故事需先写技术方案） → 编码 → 自测 → 代码审查
  - 每个组件/页面必须包含基础单元测试
  - 联调前与后端确认接口契约（Swagger/YApi）
- [ ] **每Sprint**：参与代码审查（至少审查他人2个PR），参与迭代评审演示

### 4.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 前端技术方案 (Tech Design) | Markdown | 按需（复杂故事） | `/docs/tech/frontend/` |
| 组件使用文档 | Markdown + 示例 | 随组件发布 | 组件库文档站点 |
| API接口联调记录 | 表格/注释 | 实时 | 代码注释 + 工具平台 |
| 浏览器兼容性测试报告 | Markdown | 每版本 | `/docs/test/compatibility/` |
| 前端性能基线报告 | Lighthouse JSON | 每版本 | `/docs/perf/frontend/` |

**代码提交规范**（遵循 Conventional Commits）：
```
feat: 添加用户登录页面
fix: 修复移动端导航栏错位问题
docs: 更新组件库使用文档
style: 调整按钮圆角样式
refactor: 重构表单验证逻辑
test: 添加登录模块单元测试
chore: 升级webpack至5.x
```

### 4.5 工作要求

- **代码质量**：单元测试覆盖率 ≥ 60%；ESLint零报错；SonarQube无严重/阻断级问题
- **视觉还原**：与UI稿差异 ≤ 2px（关键页面需走查）
- **兼容性**：支持 Chrome/Edge/Firefox/Safari 最新2个主版本 + 移动端适配
- **性能基线**：首屏加载时间 ≤ 2s（4G网络）；Lighthouse性能评分 ≥ 80
- **响应时效**：代码审查（PR Review）必须在提出后 4 小时内响应

### 4.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 故事点完成率 | ≥ 100%（承诺值） | 每Sprint |
| 代码审查参与度 | ≥ 100%（分配到的PR） | 每Sprint |
| 单元测试覆盖率 | ≥ 60% | 持续 |
| 生产环境前端缺陷数 | ≤ 2/版本 | 每版本 |
| 组件复用率 | ≥ 40% | 每季度 |

## 五、后端开发工程师

### 5.1 岗位定位
业务逻辑与数据的核心实现者，负责系统架构、接口设计、数据库与性能保障。

### 5.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **服务开发** | 实现业务逻辑、API接口、领域模型（DDD分层） |
| **数据设计** | 数据库表设计、索引优化、迁移脚本管理 |
| **接口契约** | 定义并维护API文档（OpenAPI/Swagger），确保前后端契约一致 |
| **性能保障** | 接口响应时间优化、并发处理、缓存与异步设计 |
| **安全合规** | 输入校验、SQL注入防护、XSS防护、敏感数据加密 |
| **单元测试** | 编写单元测试与集成测试，保障核心逻辑覆盖率 |

### 5.3 日常工作清单

- [ ] **每日**：参加站会；推进当前故事开发；处理线上告警（值班日）
- [ ] **开发中**：
  - 领取故事 → 编写技术方案（涉及数据库变更/架构调整时） → 接口设计评审 → 编码 → 单元测试 → 自测 → 提交PR
  - 涉及数据库变更：必须提交Migration脚本（Flyway/Liquibase），禁止手动改表
  - 涉及新接口：必须先更新API文档，再开始编码
- [ ] **每Sprint**：参与代码审查，参与技术方案评审会

### 5.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 后端技术方案 | Markdown | 按需 | `/docs/tech/backend/` |
| API接口文档 (OpenAPI) | YAML/JSON | 实时 | 代码仓库 + Swagger UI |
| 数据库设计文档 (ER图) | 图表 | 按需 | `/docs/design/db/` |
| 数据库迁移脚本 | SQL | 随版本 | `/db/migration/` |
| 接口性能测试报告 | 表格 | 每版本 | `/docs/test/perf/api/` |

**技术方案模板**：
```markdown
## 技术方案：XX功能
### 背景与目标
### 方案对比（至少2个方案）
| 方案 | 优点 | 缺点 | 风险 |
|------|------|------|------|
### 最终方案
### 数据库变更
### 接口变更
### 安全考虑
### 回滚策略
### 估算故事点
```

### 5.5 工作要求

- **代码质量**：单元测试覆盖率 ≥ 70%；SonarQube无严重/阻断级问题；圈复杂度 ≤ 15
- **接口规范**：RESTful设计规范；接口响应统一包装（code/message/data）；版本控制（v1/v2）
- **数据库**：所有变更必须通过Migration脚本；禁止生产环境直接执行DDL；索引设计需评审
- **性能基线**：API P95响应时间 ≤ 500ms；错误率 ≤ 0.1%；支持至少 200 QPS/核心
- **安全**：所有输入参数必须校验；敏感操作必须鉴权；日志禁止输出明文密码/Token

### 5.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 故事点完成率 | ≥ 100%（承诺值） | 每Sprint |
| 单元测试覆盖率 | ≥ 70% | 持续 |
| 接口P95响应时间 | ≤ 500ms | 持续 |
| 生产环境缺陷数 | ≤ 3/版本 | 每版本 |
| 代码审查响应时效 | ≤ 4小时 | 持续 |

## 六、测试工程师 (QA / SDET)

### 6.1 岗位定位
质量的守门员与赋能者。从"测试后置"转向"测试左移+右移"，通过自动化与流程保障提升整体质量。

### 6.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **测试策略** | 制定迭代测试计划，明确测试范围、方法、资源与风险 |
| **测试设计** | 基于用户故事与AC设计测试用例（功能/接口/性能/兼容性） |
| **自动化测试** | 搭建与维护自动化测试框架（UI/API/单元覆盖率追踪） |
| **持续测试** | 将自动化测试集成至CI/CD流水线，实现提交即测试 |
| **质量分析** | 分析缺陷分布、逃逸原因，输出质量报告与风险预警 |
| **探索性测试** | 执行自由测试，发现边界与异常场景问题 |

### 6.3 日常工作清单

- [ ] **每日**：参加站会；查看CI/CD流水线失败用例；验证已修复缺陷
- [ ] **Sprint初期**：
  - 参与需求评审，提出可测性风险
  - 设计测试用例，评审并录入用例库
  - 评估自动化测试需求，补充缺失的自动化脚本
- [ ] **Sprint中期**：
  - 接口测试（开发提测后第一时间）
  - 探索性测试（功能稳定后）
  - 性能测试（涉及性能需求的故事）
- [ ] **Sprint末期**：
  - 执行全量回归测试（自动化+核心流程人工）
  - 输出质量评估报告，给出发布建议
- [ ] **持续**：维护测试用例库、自动化脚本、测试环境

### 6.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 迭代测试计划 | Markdown | 每Sprint | `/docs/test/plan/` |
| 测试用例 | 测试管理工具 | 实时 | 工具平台（TestRail/禅道） |
| 自动化测试脚本 | 代码 | 持续 | `/test/automation/` |
| 缺陷报告 | 工具模板 | 实时 | 工具平台（Jira） |
| 质量评估报告 | Markdown | 每Sprint | `/docs/test/report/` |
| 性能测试报告 | 专业工具导出 | 按需 | `/docs/test/perf/` |

**缺陷报告标准模板**：
```markdown
## 缺陷标题：简洁描述问题
**缺陷编号**：BUG-XXX
**优先级**：P0/P1/P2/P3
**严重程度**：致命/严重/一般/提示
**所属模块**：XX模块
**发现版本**：vX.X.X
**环境**：测试环境/生产环境
**复现步骤**：
1. 步骤一
2. 步骤二
**实际结果**：...
**预期结果**：...
**附件**：截图/日志/录屏
**影响范围**：...
```

### 6.5 工作要求

- **测试左移**：需求评审阶段必须参与，可测性风险需提前提出
- **自动化覆盖**：核心流程自动化率 ≥ 80%；回归测试必须全自动化
- **缺陷质量**：缺陷报告必须包含复现步骤、环境、截图；无法复现的缺陷不超过 5%
- **响应时效**：开发提交缺陷修复后，24小时内必须验证完毕
- **发布门禁**：P0/P1缺陷未修复完毕，有权阻止发布（发布否决权）
- **测试环境**：测试环境必须独立且稳定，与生产环境数据脱敏隔离

### 6.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 测试用例执行率 | 100%（计划内） | 每Sprint |
| 自动化测试通过率 | ≥ 95% | 每日 |
| 缺陷逃逸率（生产发现/测试发现） | ≤ 5% | 每版本 |

## 七、DevOps / 平台工程师

### 7.1 岗位定位
交付流水线的构建者与基础设施的守护者。通过自动化工具链实现"一键构建、一键部署、一键回滚"。

### 7.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **CI/CD流水线** | 设计、搭建、维护持续集成与持续交付流水线 |
| **环境管理** | 管理开发/测试/预发/生产环境，确保环境一致性（Infrastructure as Code） |
| **监控告警** | 搭建日志、指标、链路追踪系统，配置告警规则 |
| **发布管理** | 制定发布策略（蓝绿/金丝雀/滚动），管理发布窗口与回滚方案 |
| **安全合规** | 镜像扫描、依赖漏洞扫描、密钥管理、访问控制 |
| **效能优化** | 优化构建速度、部署时长、资源利用率，降低云成本 |

### 7.3 日常工作清单

- [ ] **每日**：检查CI/CD流水线健康度；处理构建失败告警；响应环境部署请求
- [ ] **每周**：
  - 分析构建/部署时长趋势，识别瓶颈
  - 检查安全扫描结果，推动高危漏洞修复
  - 更新基础镜像与依赖版本
- [ ] **每Sprint**：
  - 保障Sprint发布窗口可用
  - 协助团队完成新版本部署与验证
  - 维护IaC代码（Terraform/Ansible）
- [ ] **持续**：优化流水线效率；管理云资源成本；维护运维手册

### 7.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|

### 7.5 工作要求

- **流水线可用性**：CI/CD流水线可用率 ≥ 99.5%；构建失败必须在30分钟内响应
- **发布自动化**：生产部署必须100%通过自动化流水线，禁止手动SSH上生产改代码
- **环境一致性**：测试环境配置必须与生产环境保持同步（IaC管理），偏差需记录
- **安全扫描**：每次构建必须执行镜像漏洞扫描（Trivy/Clair），高危漏洞阻断发布
- **监控覆盖**：核心服务必须配置：存活探活、错误率、P99延迟、业务黄金指标
- **发布纪律**：非紧急发布必须在窗口期执行；紧急发布需TL+PO双审批

### 7.6 考核指标

| 指标 | 目标值 | 考核周期 |

| 部署频率 | ≥ 2次/周 | 每周 |
| 发布失败回滚率 | ≤ 5% | 每季度 |
| 平均恢复时间 (MTTR) | ≤ 30分钟 | 持续 |
| 云资源成本偏差 | ≤ 预算 10% | 每月 |

## 八、UI/UX 设计师

### 8.1 岗位定位
用户体验的定义者与视觉标准的制定者。确保产品既好用又好看，设计与实现无缝衔接。

### 8.2 核心职责

| 职责域 | 具体内容 |
|--------|---------|
| **交互设计** | 设计信息架构、页面流程、交互原型（低保真/高保真） |
| **视觉设计** | 制定视觉规范（色彩/字体/组件），输出高保真UI稿 |
| **设计系统** | 维护团队设计系统（Design System），确保设计一致性 |
| **用户研究** | 组织可用性测试，收集用户反馈并迭代设计 |
| **设计交付** | 按规范交付标注、切图、动效说明，确保前端准确还原 |
| **设计走查** | 在测试环境进行UI走查，确保实现与设计稿一致 |

### 8.3 日常工作清单

- [ ] **每日**：参加站会；推进当前故事的设计工作；响应前端还原问题
- [ ] **Sprint计划前**：
  - 确认下个Sprint涉及的故事已有UI稿
  - 与PO确认交互流程与业务逻辑
- [ ] **Sprint中**：
  - 复杂交互需先输出原型并走评审
  - 设计稿发布后通知前端领取，并同步到设计协作平台（Figma/蓝湖）
  - 前端开发完成后，在测试环境进行UI走查
- [ ] **每Sprint**：参与迭代评审，收集UI/UX反馈

### 8.4 文档规范

| 文档名称 | 格式 | 更新频率 | 存放位置 |
|---------|------|---------|---------|
| 设计系统 (Design System) | 在线文档 | 持续 | 设计平台 |
| 视觉规范文档 | 在线文档 | 每季度 | 设计平台 |
| 交互原型 | Figma/Axure | 随故事 | 设计平台 |
| UI设计稿 | Figma/Sketch | 随故事 | 设计平台 |
| 切图与标注 | 导出资源 | 随设计稿 | 设计平台 + `/assets/ui/` |
| 可用性测试报告 | Markdown | 按需 | `/docs/ux/usability/` |
| UI走查报告 | 表格 | 每版本 | `/docs/ux/ui-review/` |

**设计交付标准**：
- 所有设计稿必须基于团队设计系统组件
- 必须包含：正常状态、Hover状态、点击状态、加载状态、空状态、错误状态
- 必须标注：尺寸、间距、颜色值（Hex/RGBA）、字体（字号/字重/行高）
- 多分辨率：至少提供桌面端（1440px）与移动端（375px）两套

### 8.5 工作要求

- **交付时效**：Sprint计划会前，当前Sprint所有故事的UI稿必须完成并评审通过
- **设计一致性**：所有新设计必须复用设计系统组件；新增组件需经过设计评审
- **走查标准**：UI还原度 ≥ 95%（关键页面100%）；走查问题必须在当前Sprint修复
- **响应时效**：前端提出的设计疑问，4小时内必须响应；复杂问题不超过24小时

### 8.6 考核指标

| 指标 | 目标值 | 考核周期 |
|------|--------|---------|
| 设计稿按时交付率 | 100%（当前Sprint） | 每Sprint |
| UI走查通过率 | ≥ 95% | 每版本 |
| 设计系统组件复用率 | ≥ 70% | 每季度 |
| 可用性测试问题闭环率 | ≥ 90% | 按需 |

### 10.3 Definition of Done (完成的定义)

一个用户故事要被视为"完成"，必须满足以下条件：

- [ ] 代码已提交并通过CI/CD流水线（构建+测试+扫描）
- [ ] 单元测试覆盖率达标（前端≥60%，后端≥70%）
- [ ] 代码审查已通过（至少1人Approve）
- [ ] 功能已在测试环境部署并通过自测
- [ ] 测试用例已执行通过（自动化+必要的人工验证）
- [ ] 无P0/P1级别缺陷遗留
- [ ] 相关文档已更新（API文档、技术方案、用户文档等）
- [ ] PO已验收通过（符合AC）
- [ ] 涉及数据库变更：Migration脚本已执行并验证
- [ ] 涉及UI变更：设计师已走查通过
